## 〇、本案例在作品集中的定位（三足鼎立）

本案例用于补齐作品集的**「数字员工」品类**，与既有两类交付形成互补：

| 支柱 | 品类 | 性质 | 证明的能力 |
|---|---|---|---|
| 第一足 | **业务型交付** | 真实客户项目 | 能在真实业务约束下把方案跑通、拿到客户认可 |
| 第二足 | **工程型部署** | 自研开源 / 私有化 | 能自建系统、写代码、做工程化与运维 |
| **第三足** | **数字员工交付**（本案例） | 个人自演示 Demo | **能独立完成 FDE 全链路：进客户门 → 诊断 → 交付 → 培训 → 量化** |

> **为什么需要第三足**：前两足分别证明「能做业务」和「能做工程」，但都缺一个东西——
> **一个人从零到一完整跑完 FDE 五段闭环的证据链**。本案例补的就是这段。

### 0.1 FDE 五段能力 → 交付物映射（作品集详情页骨架）

| # | FDE 能力段 | 本案例做了什么 | 可点开的证据 |
|---|---|---|---|
| 1 | **进客户门**（Discovery） | 虚构典型客户画像、现状基线、痛点排序、成功指标定义 | **D1** Discovery Brief |
| 2 | **诊断业务** | 询盘全流程梳理、三色自动化边界圈定、工作流设计、Prompt 体系、知识库分级 | **D2** 边界图 · **D3** 工作流设计 · **D4** Prompt 体系 · **D5** 知识库构建包 |
| 3 | **端到端交付** | Dify 工作流 31 节点落地、知识库 4 库重建、**六轮回归迭代 44/50 → 52/52** | **D12** 验收回归报告（含六批次全记录）· **D6** IM 接入 · **D7** 部署手册 |
| 4 | **现场培训** | 培训包、操作手册、FAQ、反馈闭环、运维交接与 SLA | **D8** 培训包 · **D9** 运营看板 |
| 5 | **数据量化** | 52 条样本全量回归、A6 三项 100%、人工介入降幅 50% | **D12** §6 · **D10** 案例复盘报告 |

> **亮点（面试可直接讲）**：第 3 段的六轮迭代是本案例最有说服力的部分——
> 从 88% 到 100%，每一轮都定位到**机制层根因**而非表面症状：
> 占位符语法 → CSV 截断 → 正则贪婪匹配 → FX 检索用错 query → **docstring 里的 `\{` 触发 SyntaxWarning 被沙箱升级为节点失败** → **纯 SKU 码检索被规则文档挤出 top_k**。
> 其中第 5 个是修第 3 个时引入的（修 bug 引入新 bug），第 6 个曾被我误判为「知识库缺数据」，靠正对照实验纠正。

### 2.5 主动披露与深挖话术（面试必备，2026-10-19 按 R-6 重写）

> **原则**：主动披露比被翻到好得多。作品集里放了完整的 D12 回归报告（含全部失败批次），
> 面试官若翻到会看到 R-1 的「A4/A5 不通过」和 R-4 的「18 条执行故障」——
> 与其被动解释，不如主动带出**六轮迭代的完整故事**。

| 被追问场景 | 建议话术 |
|-----------|----------|
| 「你这个案例做到什么程度？」 | 「**52 条覆盖三难度的验收样本，全量通过 52/52，执行成功率 100%**。六轮迭代从 44/50（88%）打到 100%，每一轮都定位到机制层根因，不是靠调 prompt 蒙过去的。」 |
| 「一开始就有这么好吗？」 | 「不是。R-1 时两条安全红线（超阈值转人工、拒答不编造）**全都没生效**，我如实记了『不通过』。根因是 LLM prompt 只是软约束、代码校验缺结构硬校验、SKU 与底价数据没进代码层。修复方案是新增一个规则兜底节点 N12b，把安全红线从『模型自觉』改成『代码兜底 + 失败即拦截』——现在是 14/14 拒答类零金额、T16/T17 全部正确转人工。」 |
| 「最难的 bug 是哪个？」 | 「两个。一个是 **docstring 里写了正则示例 `\{`，触发 Python 的 SyntaxWarning，被 Dify 沙箱升级成节点失败**，整个节点 18 条样本全炸，而且报错不指向代码。另一个是**纯 SKU 码做检索 query 时召回失败**——我一开始误判成『知识库缺数据』，后来做了正对照实验才发现：库里数据是全的，是规则类文档抢占了 top_k 名额，把价格表挤出去了。改成『原文 + SKU + 品类词』并把 top_k 从 4 提到 10，出单量从 3 张恢复到 6 张。」 |
| 「自动化率达标了吗？」 | 「这里我要主动说明一个**指标设计问题**：原本定的『闭环率 ≥40%』，但 52 条样本里期望可闭环的只有 20 条，**理论上限就是 38.5%，数学上永远达不到**。这个指标测的是样本构成，不是系统能力。我把它改成了三项行为正确率——自动闭环 20/20、报价草稿 6/6、强制转人工 26/26，全部 100%。**这比硬凑一个 40% 更能说明问题。**」 |
| 「成效数字可信吗？」 | 「分两层：**能力正确性**用实测（52/52、A6 三项 100%，都有回归 JSON 可复现）；**人力节省**用测算模型（月 880 条基线，保守档 29.3 工时/月 ≈ 0.17 FTE，目标档 46.9 工时 ≈ 0.27 FTE），并明确标注基线是假设值。**两者不混算**——样本集是为覆盖边界设计的，构成不等于真实流量，我不会拿它直接推客户的 FTE。」 |
| 「为什么把失败的过程也放进来？」 | 「因为作品集要证明的是**交付方法和工程判断**，不是证明我每次都一次做对。能自己定验收标准、自己跑回归、自己定位根因、自己定义修复范围——这套闭环比一个漂亮数字更能说明 FDE 的核心能力。」 |
| 「哪一段还没做完？」 | 「**Phase 2 企微接入和 Phase 3 现场部署没做**，我如实标注了。Phase 1（搭建+验收）已完全收口，Phase 4 的数据口径已具备但看板待回填。我不会把方案态写成已实施。」 |
